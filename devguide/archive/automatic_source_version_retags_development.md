# Automatic source binding retags development as a release

**Reported:** 2026-10-06, source workflow follow-up
[37543266635](https://github.com/uibcdf/molsysviewer/actions/runs/37543266635),
commit `e0ae8a05099fce944b45355387f44d23d9458b13`.

## What

The #173 correction extends canonical Viewer tagging to automatic events.
Linux returns 2,890 passed, 27 skipped, one failed: the existing
`test_source_pair_main_pushes_validate_development_without_retagging_releases`
guard rejects that condition. macOS also fails. The earlier bounded closure
selection omitted that neighboring policy guard; its pass was insufficient.

## How

Explicit candidate dispatches may bind the canonical version. Automatic source
pushes must keep development provenance. Restore that event boundary, rebuild
`build:runtime` from the Python version generated by the development installation,
and reinstall the source Viewer so installed and source exports use that runtime.
Perform this before provider/resource audits, integration and the full Python suite.
Do not rewrite JS package metadata or replace public tags. Reuse the runtime in
Linux's later browser block; explicit canonical dispatches keep their existing build.

## Why

The source pair must validate coherent development provenance and survive an
existing public release tag on a different commit. The fixed 0.24.0 build 1
package and canonical source run remain unaffected: the sixteen installed
staging cells, exact Windows launchers, 39 hosted core suites and three canonical
native source regressions pass. This is a workflow-only correction.

## What was refuted

Changing the existing policy assertion would hide the regression. The initial
unconditional-tag approach belongs to #173's preserved report; append a dated
correction there rather than rewriting that archived claim. Staged artifacts
must not be rebuilt or relabeled for this developer-tooling correction.

## Resolution

The workflow restores dispatch-only candidate tagging. Development now builds
its runtime and reinstalls Viewer before every source audit/test; Linux reuses
that runtime later. All 11 policy/workflow guards pass, including the preexisting
no-retagging rule. The new guard fails if rebuilding/reinstalling is omitted or
moved after source validation. An isolated venv backed by the recorded staged
provider runs the exact development pipeline: initial version
`0.23.4+110.ge0ae8a05`, rebuilt runtime with that identity, reinstall version
`0.23.4+110.ge0ae8a05.dirty`. Their release families agree, as required for
development exports. All eight actual offline WebGL export cases pass in
41.60 seconds; all loaded scientific modules retain their recorded installed
origins and `pip check` passes. This is bounded development-tooling evidence,
not a replacement artifact or another full regression. The next automatic
hosted source run remains a separate follow-up after the correction is pushed.
