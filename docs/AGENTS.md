# Documentation Agents Guide

This guide is for agents and contributors editing documentation under `docs/`
and other markdown-based guides in this tree. It refines the global rules in
the repository root `AGENTS.md`.

## Language, style, and tone

- All documentation must be written in English.
- Follow the writing style described in `docs/content/developer/docs.md` and `docs/content/developer/documentation/web/editorial_guidelines.md`:
  short, direct sentences, user-focused (“you”), and consistent terminology with the API.
- Summaries and headings for functions or tutorials should use gerund phrasing when matching docstrings (for example, "Visualizing molecular structures.").
- For scientific quantities, always mention units explicitly (nm, Å, ps, radians, elementary charge).

## Variable Naming Policy

- In all user guide tutorials, code examples, docstrings, and documentation notebooks:
  - The canonical variable name representing a **MolSysViewer view instance** MUST be `view` (NOT `v` or `viewer`).
  - When multiple view instances are manipulated without specific descriptive names, use `view_A`, `view_B`, `view_C`, etc.
  - The canonical variable name representing a **single molecular system** MUST be `molsys` (NOT `mol`).

## Markup and MyST/Sphinx usage

- Pages under `docs/content` use Markdown/MyST with Sphinx directives.
- Use MyST admonition syntax for blocks such as:
  - `:::{admonition} API documentation ... :::`
  - `:::{seealso} ... :::`
  - `:::{versionadded} 0.8.0 :::`
- Use `{func}` and related roles for cross-references to API objects, and keep anchors stable.
- Prefer labeled sections plus `{ref}` for internal links between documentation pages instead of hard-coding file paths; see `docs/content/developer/documentation/web/references.md` for detailed patterns.

## Structure and file layout

- Respect the existing structure under:
  - `docs/content/user/` for user guides, tutorials, and conceptual docs.
  - `docs/content/showcase/` for interactive demos and feature showcases.
  - `docs/content/developer/` for developer documentation.
  - `docs/api/` for autogenerated API references.
- Do not modify or overwrite autogenerated outputs in `_build/`, `_gettext/`, `_locale/`, or other generated directories.
- Template and theme assets in `_templates/` and `_static/` should only be changed when adjusting global look-and-feel, and changes should be minimal and coordinated with `conf.py`.
- **File Format Policy (`.md` vs `.ipynb`)**: Documentation pages that contain only narrative text, layout grids, conceptual overviews, or static cross-references (such as index pages and section portals) MUST be created as MyST Markdown (`.md`) files. Jupyter Notebooks (`.ipynb`) MUST only be used when there is a clear technical justification, such as executable Python code cells, dynamic outputs, or interactive 3D visualizations.

## Governance and Micro-`AGENTS.md` Model

- **Rule Resolution Hierarchy:**  
  `Root AGENTS.md` ➔ `docs/AGENTS.md` ➔ `[Subdirectory]/AGENTS.md` ➔ `[Page_Name].AGENTS.md` (Most specific wins).
- **Micro-Governance Files (`[Page_Name].AGENTS.md`):**  
  Major documentation pages or notebooks (e.g. `docs/index.ipynb`) are paired with a micro-governance file (e.g. `docs/index.AGENTS.md`).
- **Content Protection Contract:**  
  Micro-governance files serve as a contract that defines frozen, inviolable content (essential concepts, code examples, PDB IDs, admonitions, and MyST section anchors) that must be preserved when refining or updating that page.
- **Documentation Manifest (`docs_manifest.yml`):**  
  All documentation sections and paired governance files must be tracked in [`docs/docs_manifest.yml`](docs_manifest.yml).

## Notebook Compilation & 3D Visualization Policy

- **Visualization Backend Policy:**  
  **MolSysViewer** is the mandatory default 3D viewer across all documentation pages and tutorials.
- **Transparent Background Policy:**  
  All static 3D views exported via `view.export.html(..., background="transparent")` MUST specify `background="transparent"` for instant dark/light theme transitions without visual lag or blink.
- **Pre-Generation Script Rule:**  
  Static HTML views MUST be pre-generated via scripts under `docs/generate_static_views/` and committed to `docs/_static/views/`. Views MUST NOT be generated on-the-fly during notebook execution, preventing Git repository bloat from multi-megabyte trajectory files.
- **Notebook execution:** Sphinx does not execute notebooks (`nb_execution_mode="off"`). Freeze tutorial outputs using `docs/execute_notebooks.py`.

## Safety and maintenance

- Keep examples minimal but complete enough to be copied and run by users.
- When reorganizing sections or navigation (for example, `index.ipynb` or `content/*/index.md`), update toctrees and verify that Sphinx builds successfully with `make -C docs html`.
